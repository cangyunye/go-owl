# 能力（处置脚本/剧本）录入技能

产出「脚本本体 + 能力元数据」的合规组合，供 owl 告警自愈匹配管线消费
（设计背景见 `docs/design/05_CAPABILITY_MATCHING_SPEC.md`）。

生成或修改元数据前必须先阅读本项目 `skills/capability/schema.md`（能力元数据唯一
schema 依据），严格按其字段与取值生成。

## 工作流

### 1. 澄清（仅当信息缺失，一次问完）

- **修什么问题**：症状描述；能否对应内置告警类型（对照 schema.md 告警类型表）
- **形态**：单脚本即可，还是多步编排（是 → 建议做成剧本，走剧本 meta 扩展）
- **风险边界**：是否重启服务 / 删除文件 / 变更网络配置；操作是否可逆
- **参数**：哪些值需要运行时确定（保留天数、服务名、路径），能给默认值的给默认

用户未说明且不影响产出的，不要追问，直接按 schema.md 给默认值。

### 2. 写脚本本体

按 schema.md「安全红线」约束：

- 幂等、有超时意识、优先非破坏性命令
- shebang 明确解释器，与元数据 `language` 一致
- 破坏性操作必须前置条件判断（磁盘阈值、白名单、确认标记）
- 参数用 `$1..$n` / `getopts` / `argparse`，提供 `usage()`

### 3. 生成元数据（静态分析优先，逐项过 schema.md）

- shebang → `language`；`getopts`/`$N` → `parameters`；危险模式 → `risk`/`destructive`
- `description`：一句话「做什么 + 对什么问题有效」
- `symptoms`：≤3 条、告警现场会出现的自然语言短语（写法细则见 schema.md）
- `alert_types`：能对上内置告警类型就必须填（零成本确定性命中）

### 4. 交付

向用户展示：

1. 脚本全文
2. 元数据 YAML 块
3. **待确认清单**（表格：字段 → 取值 → 依据/静态分析信号）
4. 明确提示：AI 草稿经人工确认后才会以 `reviewed=true` 入库，未审核的能力不参与自动匹配

## 边界

- 只产出脚本与元数据草案，不直接执行、不修改既有库内容；入库由用户在 Web 脚本库/剧本库完成
- `risk` / `destructive` 如实标注，不得为绕过审批而标低
- 不发明 schema.md 之外的字段；不确定的取值宁可留空让用户补
- 目标告警类型对不上时不编造 OWL-ID，`category` 兜底为 `generic`
