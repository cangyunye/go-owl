# v1.12.0 变更记录

本版本包含 **6 个提交**，主题是**监控存储架构重构**：指标/告警从 owl.db 拆分到独立的 metrics 库，
并把采集改为默认关闭 + 写入量估算，彻底解决数百节点规模下数据库写锁拖垮 Web/TUI 的问题。

## 🚨 升级须知（重要）

- **监控采集默认关闭**：`monitor.enabled` 未设置时不再自动开启。需要在设置页「监控告警」卡片
  显式打开，并先用新增的「写入量估算」评估磁盘占用。
- **历史指标数据随旧表清理丢弃**：服务首次以本版本启动时，会自动 DROP 掉 owl.db 里遗留的
  `metrics_YYYYMM(DD)` 分区表（可再生的监控采样，保留期本就只有 30 天）。如需保留个别关键
  历史指标，请在升级前单独导出。
- 升级后 `owl.db` 体积不会立刻缩小：DROP 只把页移入 freelist，请在低峰期到设置页
  「数据库」卡片执行一次 **VACUUM** 把空间归还操作系统（数百 MB~几十 GB 库需数分钟）。

## 🏗️ 监控存储拆库重构

此前指标/告警内嵌在业务库 owl.db，数百节点（如 500 台 × 60s 采集 ≈ 2000 万行/天）下：

- 每日清理 `DELETE FROM metrics_YYYYMM WHERE ts < ?` 无索引全表扫描，持写锁 1~2 分钟；
- 整月过期后的 VACUUM 重写整个业务库（含节点/用户/历史），需双倍磁盘空间；
- 期间 Web 更新节点分组返回 500、TUI 保存报 `database is locked (5) (sqlite_busy)`，
  退出 owl-serve 才能写入。

本次改动：

- **指标与告警落独立 `<主库>.metrics.db`**（如 `~/.owl/owl.db` → `~/.owl/owl.metrics.db`），
  清理/VACUUM 不再触碰业务库
- **分区按天**（`metrics_YYYYMMDD`），过期整天 `DROP TABLE`（毫秒级、零扫描），
  取代全表扫描 DELETE
- **建表缓存**：修复每轮每节点 `CREATE TABLE IF NOT EXISTS` 并发 DDL 的 schema 锁冲突
  （绕过 busy_timeout 约 4ms 即失败，每轮随机丢 1~2 台节点指标）
- **每轮聚合一次入库**：引擎先并发采集、统一落库，取代"每节点一个事务"
  （500 台时每分钟数百次写锁争抢）
- **告警分组筛选跨库解析**：`Store.SetNodeGroupResolver` 注入主库解析器，解析失败退化为
  不过滤（与拆库前容错一致）
- 清理/VACUUM 成功也记录耗时日志（`monitor_cleanup`），此前成功时完全静默，
  长事务期间业务写撞锁无从对账

## ⚡ 锁竞争缓解

- 主库/CLI DSN `busy_timeout` 5s → 15s：janitor 历史清理等偶发长事务期间，写操作先排队
  而不是立即失败
- **TUI/CLI 节点写操作（Add/Update/Remove/BulkUpsert）对 SQLITE_BUSY 退避重试**
  （再补 300ms/600ms 两轮），重试耗尽仍失败则提示
  「数据库被其它进程占用（owl-serve 可能正在清理，请稍后重试）」并保留底层错误，
  不再是裸的 `database is locked (5)`

## 🖥️ Web 设置页

- 监控卡片新增**「写入量估算」计算器**：节点数（默认带入当前总数）× 每轮约 25 项指标 ×
  采集间隔 × 保留天数，实时算出每天写入行数/体积与指标库稳态大小，超 10GB 高亮提示。
  例：500 台 × 60s × 保留 30 天 ≈ 每天 1800 万行（约 1GB/天），稳态约 30GB
- 启用说明注明默认关闭、指标存独立 metrics 库、写入量需评估；开关勾选态与服务端对齐
  （仅 `monitor.enabled=true` 时勾选）

## ⚙️ 运维建议（500 台规模）

- 采集间隔建议 300s（10 分钟），保留天数按磁盘余量在估算器里评估
- 紧急修改节点时无需再退出 owl-serve：正常写操作已具备 15s 排队 + 重试兜底
