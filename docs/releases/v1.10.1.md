# v1.10.1 变更记录

本版本包含 **1 个提交**，是 v1.10.0 的修复版本：修复真实环境中剧本执行"单步卡住数小时、运行中零反馈"的问题（用户实测 fail_continue 8 小时只执行 5 步、pipeline 第一步起完全卡住）。

## 🐛 问题修复

### 执行中步骤不可见（长任务零反馈）
- **根因**：v1.9.1 的逐步推送在**步骤完成之后**才触发——长命令/脚本/上传执行期间没有任何事件，前端只显示「0/N 步 · 暂无步骤结果 + running」，用户无法知道当前卡在哪一步、哪个节点、卡了多久。
- **修复**：
  - 执行器新增 `SetStepStartFunc`：每个节点步骤**开始执行**（RunAction 之前）即回调
  - 引擎维护执行中步骤注册表（仅内存、不落库），步骤开始即进入、完成即移除
  - `running_steps` 快照随 WebSocket 广播与 REST `GET /playbook/runs/:id` 一同下发（口径一致，页面加载/WS 断线轮询也可见）
  - 前端步骤表顶部渲染 running 徽章行（复用既有脉动样式），进度行追加「执行中 N」

### 单步可无限卡死，拖死整个 run
- **根因**：步骤级 watchdog 在 SSH 连接建立**之后**才启动，`NewSession` 等连接/会话层的阻塞点不响应 ctx；执行器与引擎之间也没有整体兜底。任何一步挂死，fail_continue 停在原地、pipeline 直接卡死，且取消只能中断已覆盖的路径。
- **修复**：`webCommandExecutor.ExecuteOnNode` 外层硬超时——整个步骤（黑名单检查、dial、会话、执行）在独立 goroutine 内运行，超过步骤超时（默认 5 分钟，任务级 `timeout.command` 可调）即强制返回失败并附明确错误「命令执行超时(N)，步骤被强制中止」；fail_continue 下后续步骤自动继续。

### 进度写库同步阻塞执行器
- **根因**：步骤回调内同步执行 `AppendResult` + 命令历史写库 + 广播。数据库被监控长事务/VACUUM 等占用时，执行器被拖住——与 v1.10.0 修的「HTTP 读被长事务卡死」同源，但当时只放开了 HTTP 读，执行器路径未解耦。
- **修复**：步骤事件先进内存队列（1024 缓冲），专职 writer goroutine 串行落库并广播；执行器回调只做入队，**执行器永不等待数据库**。运行结束先等 writer 排干再写终态，保证 results 完整。

### 引擎 panic 无兜底
- **修复**：run goroutine 加 recover——panic 时 run 标记 failed 并写入「执行引擎内部错误(panic)」+ 堆栈日志 + 广播，不再永远停在 running（或带崩进程）。
- 顺带修复：`AppendResult` 写库失败时此前直接 return 跳过广播，现在失败也广播，前端至少能看到实时状态。

## ✅ 回归测试

- `TestExecuteOnNode_HardTimeout_WhenRunnerIgnoresContext`：底层执行器完全无视 ctx（连接层挂死最坏情况）时，外层硬超时必须强制返回
- `TestExecutePlaybookRunV2_RunningStepVisibleWhileInFlight`：步骤执行中（未完成）广播必须携带 running_steps，完成后清空并转入 results
- `TestStepStartFunc_FiredBeforeExecution`：步骤开始回调在执行前触发、when 跳过不触发

## 🔬 验证

- E2E（进程内真实 SSH + 真实执行）：慢步骤（sleep 600）执行期间 REST 轮询即可见 `running_steps=[slow_in_flight running]`；挂死命令 3s 任务级超时强制失败（错误含「外层硬超时」），fail_continue 后续步骤正常完成
- `go test ./... -race` 全绿

## ⚠️ 升级注意

- 外层硬超时等于步骤的命令超时（默认 5 分钟）：确有超长命令的剧本请为该任务显式配置 `timeout: {command: ...}`，否则会在 5 分钟被强制中止
- 旧版本卡在 running 的历史 run 不会自动恢复，可在界面上取消归档
